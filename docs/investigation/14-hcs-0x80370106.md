# HCS 0x80370106 故障与停止规则 / HCS 0x80370106 failure and stop rules

> 本文独立记录 `0x80370106` 的强制停止规则、已执行操作、实证日志和恢复边界。
> 通用容器桌面调查见 [13-container-desktop-and-rdp.md](13-container-desktop-and-rdp.md)。

## 1. 强制停止规则 / Mandatory stop rule

只要新出现 **`0x80370106`**，立即停止所有 HCS、UDK、gRPC、直接 VM 和官方 Windows Sandbox
启动及实验。不得重试、继续字段矩阵、清理平台资源、重启服务或把其他传输/配置误判为可行替代。
先保留错误原文、时间、调用、实例 ID、镜像/模板 ID 和已执行操作，然后等待人工恢复。

以下错误本身**不是**该硬停止条件，但仍须根据证据诊断，不能当作接近成功：

- `0x80070003`：路径不存在；
- `0x8007000D`：数据或配置无效；
- `0xC0370400`：本次调查中表现为 vSMB 保存状态恢复失败。

禁止以试错为目的执行 DISM、Windows 功能重置、服务重启、Windows 更新卸载/回滚、注册表删除，
或删除基底镜像、CMS 模板、prepared storage。禁止进程注入和 API 钩子抓取 CMS 配置。

## 2. 用户验证过的恢复流程 / User-verified recovery

用户确认：出现此错误后，单纯重启不能恢复。当前验证过的流程是卸载 **Windows Sandbox、容器、
容器服务器**，重启电脑，再安装这些功能，并启动一次官方 Windows Sandbox 完成恢复检查。

这是人工平台恢复流程，不是本项目的产品引擎或验收替代。恢复前不得继续直接 HCS 实验。
不要在本项目中自动执行上述卸载、重启或安装操作。

## 3. 2026-10-28 最新触发记录 / Latest trigger

本轮先将 `main` 合并到 `feat/windows-container-desktop`（merge commit `35b680a`），修复一处合并后的
RAIL 启动列表空引用（`9081451`），标准完整测试达到 **543/543 通过**。

当时误以为本机 `hcs-rdp-074400` 曾以空 guest state 越过 Start 并写盘，据此试验一个变量：
新差分 VHD 仍引用平台 prepared base，保留当前 `GuestConnection`，但新 VM 的 `sandbox.vmgs`
改由 `HcsCreateEmptyGuestStateFile` 创建，不再复制 donor vmgs。没有加入 `RestoreState`、VMRS
或模板参数。后续字节级复核推翻了这一前提：074400 的 guest state 与平台 donor 具有相同 EFI 分区
GUID `e597a399c201ae42a2df3fb196b561f5`，是 donor 副本经 guest 写入后的文件；真正空 guest state
属于本次 104749 实验，EFI 分区 GUID 为 `23742ac8…`。因此不能再声称 donor guest state 导致 vSMB
恢复失败；`0xC0370400` 出现在额外的 `RestoreState`/模板恢复路径，而 074400 的 donor + 无 RestoreState
组合曾实际启动并写盘。

TDD 的 RED 为 23/24（期望 `empty-vmgs`、实际 `child-vmgs`）；最小实现后的存储/JSON 测试为 37/37，
完整测试为 543/543。随后仅执行一次直接 HCS 启动：

- 实例：`45ffa743-2a62-4e93-ae7b-0b9bccaa07aa`；
- Create 成功；
- 约 6.5 秒后，`HcsStartComputeSystem` 返回 **`0x80370106`**；
- 未达到 HCS Running + `vmwp` 持续 140 秒及 guest exec 门槛，未进行 RDP/RAIL 验收。

错误归因：

```text
ErrorMessage: 虚拟机或容器意外退出。
OperationFailure: Detail=Start
SystemExit: Detail=Shutdown, Initiator=GuestOS
WorkerExit: Type=StoppedOnReset, Detail=Reset, Initiator=GuestOS
```

发现错误后立即停止全部 HCS/VM/Sandbox 启动、查询和进一步实验，没有重试、清理平台资源或重启服务。
未通过真实验收的产品及测试改动已撤回，未提交、未合并；保留的提交只包含文档和此前已通过完整测试的
main 合并/UI 合并回归修复。

## 4. 可能原因与证据边界 / Possible causes and limits

HCS 返回的归因只证明 guest OS 在 Start 期间 Shutdown/Reset。结合用户确认的平台未受损结论，当前
主要怀疑空 guest state 与 prepared-base 的首次启动/特化契约不匹配，但这一点仍未由平台内部日志证明。
历史代码对比显示：2026-10-14 guest exec 成功时与当前的 JSON 构建器、prepared-base VHD 链、donor
guest-state 复制及 `GuestConnection` 契约一致，句柄生命周期也不是本次 Start 失败的成因。

因此下一步不是继续换字段，而是用未修改的历史良好配置做一次直接 HCS 验证。不得再把 074400
描述成空 guest state 成功案例，也不得把 donor guest-state 复制与额外的 `RestoreState` 恢复混为一谈。

### 用户确认与恢复调查（2026-10-28 后续）

用户随后明确确认：**刚刚的操作并没有搞坏 HCS 系统**。因此本次 `0x80370106` 记录为直接启动配置下的
guest OS Shutdown/Reset，不再将“平台已损坏、必须人工重装恢复”作为本次事件的结论，并解除本轮阻塞。
这是对用户现场结论的如实记录，不冒充独立平台验证；今后新出现 `0x80370106` 时仍执行第 1 节的
强制停止规则。后续调查先对比历史上 guest exec 成功的直接 HCS 版本，不重复同一次失败启动。

### 历史良好配置再次失败（2026-10-28 11:42）

随后使用未修改的历史良好配置做了一次直接 HCS 验证：prepared-base 差分 VHD、donor guest-state
副本、现有 `GuestConnection`，无 `RestoreState`，没有任何新产品代码或 JSON 字段改动。聚焦测试
37/37 通过，CLI 构建成功。实例 `ca7143c3-39de-4bf0-916c-d7b92e3f4908` Create 成功，但约 6.5 秒后
`HcsStartComputeSystem` 再次返回 **`0x80370106`**，归因仍为 GuestOS Shutdown/Reset。

本次失败后已再次停止全部 HCS/VM/Sandbox 工作，未进行 RDP/RAIL 或持久化验收。目标 ID 最终不在
HCS 列表，`vmwpCount=0`，无对应 host 进程；仅存在平台既有 `SavedAsTemplate`。清理中的
`hcsdiag terminate` 只打印帮助并返回 1，不声称终止成功；失败实例是自行消失。完整记录见
`.superpowers/sdd/2026-10-28-direct-hcs-vm-rdp-rail/task-1-baseline-report.md`。

这次结果否定了“只要恢复 donor guest state 就能启动”的假设，说明空 guest state 不是唯一失败条件。
此前用户关于平台未受损的确认只对应前一次事件；本次新事件不擅自推断平台是否损坏，也不继续启动
来试探。等待用户给出新的处理结论。

### 指定 vGPU-off 官方配置诊断成功（2026-10-28 后续）

按用户随后给出的诊断流程，只启动一次官方 Windows Sandbox，配置为：

```xml
<Configuration>
  <vGPU>Disable</vGPU>
  <Networking>Enable</Networking>
</Configuration>
```

配置文件为 `artifacts/hcs-vm-fix-20261028/diagnostic-vgpu-off.wsb`。官方
`WindowsSandboxRemoteSession` 窗口打开且 `Responding=True`，主机截图显示独立 Sandbox 桌面，
没有再次出现 `0x80370106`。截图证据为
`artifacts/hcs-vm-fix-20261028/diagnostic-vgpu-off-screen.png`。

这证明当前平台能够通过该官方配置打开 Sandbox，解除本次人工恢复阻塞，但不证明 vGPU 是直接 HCS
GuestOS Reset 的根因。直接 HCS JSON 当前没有独立 vGPU 设备字段；`EnhancedModeVideo` 是 RDP 端点，
不能与 GPU 开关混为一谈。后续只读对比视频/恢复契约，取得新证据前不重复直接启动。

### 第三次直接启动与最小模板继承探针（2026-10-28 15:29 后）

在第一次官方 vGPU-off 诊断成功后，使用当前未修改的直接 HCS 产品路径再次启动，实例
`cc2ae2f9-dc3c-4637-8496-50b57fbdd93d` 仍在 `HcsStartComputeSystem` 返回 `0x80370106`。
按用户指定流程再次以同一 vGPU-off 配置启动官方 Sandbox，官方实例
`24379c99-d64c-4e72-9249-861be1a2cfff` 成功 Running，远程窗口响应且有真实桌面；公开属性确认其
`RuntimeTemplateId=b24a3fff-3991-45e4-aeec-e677de0355c7`。最新截图为
`artifacts/hcs-vm-fix-20261028/diagnostic-vgpu-off-screen-latest.png`。

随后没有修改产品，只用一次性 HcsProbe 验证“模板提供设备状态、调用方只补必需拓扑”的架构：

| 实例 | 配置 | 结果 |
| --- | --- | --- |
| `d5f9a75d-57ed-4c6f-a4ad-7e7ac43a9980` | 仅 `TemplateSystemId` | Construct `0x8037010D`，缺少必需 `Chipset` |
| `1a55d1de-934a-4f0e-a6f7-bea84e69bb7c` | 仅补 Chipset | Create 成功，Start `0x80070057`，无法初始化内存 |
| `a0f51f4c-508c-4da3-a4f1-e5efde14d641` | 再补内存/CPU 拓扑 | Start `0xC0370029`，保存状态与物理机不兼容 |
| `b19ef529-d8a6-4e4a-bb91-f93d33924a27` | 仅将 `SynchronizeHostFeatures` 改为 false | 同一 `0xC0370029`，未解决 |

微软 [HCS JSON Schema Reference](https://learn.microsoft.com/en-us/virtualization/api/hcs/schemareference)
只定义 `TemplateSystemId` 为克隆模板 ID，并未证明省略设备树会继承全部必需拓扑。以上实际错误表明
当前模板恢复仍依赖完整且匹配的创建契约；`SynchronizeHostFeatures` 不是该兼容性错误的单独修复。
没有继续字段矩阵，没有将探针改动写入产品，也没有开始 RDP/RAIL/持久化验收。用户说明本机有两个 GPU，
Windows Sandbox 对其兼容性不佳；后续可把“选择分配给 VM 的 GPU”作为独立增强项，但不能用它替代
当前直接 HCS 启动契约的修复。

### CMS 原生创建探针（2026-10-28 后续）

为避免继续猜测 HCS JSON，静态读取了官方 `WindowsSandbox.exe` 与 `cmclient.dll` 的公开调用面。
官方以类型 `5` 和访问掩码 `0xF00FF` 调用 `CmsCreateContainer`。原生导出确认第一个参数是指向
GUID 的指针，第三个参数是配置结构体，配置版本位于 `0x70` 且只接受 `1` 或 `2`；访问掩码与配置
偏移 `0x0C` 的标志不是同一字段。

一次性探针从错误字符串签名修正到上述 ABI 后，`CmsCreateContainer` 能进入 RPC，但版本 `1` 的
空/默认配置仍返回 `0x800706C5`。这说明还缺官方构造的存储/设备配置内容，不能把“已进入 RPC”
当作创建成功。没有修改产品或启动第二个伪造引擎，没有以 UDK/gRPC/官方 Sandbox 充当本项目验收。
相关静态证据和日志在 `artifacts/hcs-vm-fix-20261028/cms-*.txt`、`cms-call-sites.txt`、
`cmsprobe*.log`。后续需要完整 CMS 配置契约，不能再继续空配置试错。

后续只读对照确认，官方属性查询 `'{}'` 只返回 ID、Owner、RuntimeTemplateId、State 等公开状态，
不能据此还原完整创建配置（`artifacts/hcs-vm-fix-20261028/official-props-20261028-175302.txt`）。
按官方默认布局补齐版本 1 配置后，一次性原生创建仍返回 `0x800706C5`
（`artifacts/hcs-vm-fix-20261028/cms-v1-create.log`）。版本 2 探针的真实 `ncalrpc` callback
binding、接口与 endpoint 注册均成功，但唯一一次 `CmsCreateContainer` 返回 `0x80070006`
（`artifacts/hcs-vm-fix-20261028/cmsv2probe/create.log`）。两次均未创建或启动 VM，均不是
`0x80370106`，也未进行 RDP/RAIL 验收。

只读复核还确认：`+0x48` 是 SID 字符串指针列表，`+0x50` 是 HvSocket 配置，`+0x18` 是
nullable `UInt64 *`（`artifacts/hcs-vm-fix-20261028/cms-config-pointer-review.md`、
`cms-config-pointer-evidence.txt`）。这些事实尚未最终定位创建失败的根因。
